# Graph Daily Sync -- Incremental Knowledge Graph Update

Keep the knowledge graph current at the end of the day. Only processes files that changed
today, so it runs fast. Can be added as a final phase of `/eod`.

Since the graph is **derived from metadata**, there is no inline wiki-link pass. `Graph/index.md`
and the MOCs are regenerated by `scripts/graph-render.py` from frontmatter plus the concept
index. Links are written only as **structural edges** (a `## Related` line to a hub on a new doc,
a registry row for a new entity page), always path-qualified. The "link every first mention in
prose" convention (which existed for Obsidian's graph view) is retired.

**When to use:** Daily, after your other EOD work is done.

---

## Phase 1: Identify Changed and Deleted Files

Find files created, modified, or deleted since the last run. Prefer git when the vault is a repo:

```bash
git -C "$VAULT" diff --name-status --diff-filter=ACMRD HEAD~1 2>/dev/null
# fallback when there is no useful history:
find "$VAULT" -name "*.md" -mtime -1
```

Exclude `.claude/`, `.obsidian/`, `_generated/`, `scripts/`, `Templates/`, and `Graph/` (those
are outputs or non-content). If nothing changed, report "No changes today" and skip to Phase 5
(render + stats only).

---

## Phase 2: Frontmatter on Changed Files

Canonical schema: see "Frontmatter Schema" in CLAUDE.md. Required minimum is `type` + `created`;
add `status`, `updated`, `tags`, `client` where applicable.

For each changed file, add or complete frontmatter using the classification rules in
`/graph-sync` (type from path, client from path, status/updated). Set `updated` to today when you
edit a file.

Report: `Frontmatter: N files checked, N updated`

---

## Phase 3: Structural Edges on New Files

Only on files **created** in this interval. Never add inline links in prose, and never touch
links in existing files.

1. A new authored doc under a client folder, your internal/company folder, `Projects/`, or
   `Resources/` that has no `## Related` section and no link to its hub gets one `## Related`
   line pointing at its hub (the client's Company Profile, the concept page, or the SOP it
   implements), path-qualified, e.g. `[[Work/Clients/Acme/Company Profile|Acme]]`. Skip records
   (`type: transcript`, daily notes) and anything under a private folder (default `Personal/`).
2. A new entity page (`Resources/People/`, `Resources/Concepts/`) gets a row in
   `Graph/entity-registry.md`.

Report: `Edges: N Related sections added, N registry rows added`

---

## Phase 4: Knowledge Extraction from Transcripts

For each changed file that is a transcript (`**/Transcripts/` folder or `type: transcript`):

1. Read the transcript.
2. Extract 2-5 key takeaways (decisions, action items, important facts). If the frontmatter
   already has `key_takeaways`, do not re-extract; count it as already extracted.
3. Push each takeaway to the relevant entity page (usually the client's Company Profile): add to
   a `## Recent Decisions` or `## Recent Activity` section with a source backlink
   `-- [source](relative/path/to/transcript.md)`, newest at the top.

If no transcripts changed, skip this phase.

Report: `Transcripts: N processed, N takeaways extracted`

---

## Phase 5: Render the Graph

`Graph/index.md` and the MOCs are generated, never hand-edited:

```bash
python3 scripts/graph-render.py --json _generated/vault-hygiene/graph.json
```

It reads frontmatter plus the concept index (`_generated/vault-hygiene/vault-index.json`, when
present) and rewrites only the files whose generated body changed (a quiet day changes nothing).
Deleted files drop out automatically. The JSON export is the node/edge data for a graph viewer.
If the command fails, say so and do not claim the graph is current.

Report the renderer's one-line summary.

---

## Summary

Write a brief sync report to `/tmp/eod-graph-YYYY-MM-DD.md` so the daily note can reference it.

```
Graph sync: N files processed, N edges added, N takeaways extracted, graph rendered (changed: <files or none>)
```
